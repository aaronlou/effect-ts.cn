# 给已发布的两篇掘金文章补的插入段落

目的：文章链接全都指向文档页，**没有任何一条指向站内的 AI 入口** —— 实测 `/api/knowledge/ask` 与
`/api/knowledge/explain` 的请求数都是 **0**。不是功能不好，是没人知道它在哪。

两条纪律：

1. **只推验证过的能力。** 实测：报错诊断（贴报错 → 定位到相关文档小节 + 可点回的引用）表现好；
   通用自然语言问答经常如实回答"文档里没讲"。所以**主推报错诊断**，不吹通用问答。
2. **必须写明边界。** 第一篇文章讲的正是类型报错，而报错诊断对"只含类型名、没有 API"的报错
   定位不准。读者一贴就发现不行，比不推更伤。

---

## 插入段 A —— 给第一篇《Effect 的类型报错怎么读》

**放哪里**：放在 5 个例子之后、「一个真正有用的技巧」之前。
理由：读者刚看完 5 条真实报错，已经建立"报错里出现的 API 名是重要线索"这个直觉 ——
这时候告诉他"有个工具就是靠这个线索做定位的"，逻辑最顺，也最容易点。

**插入内容（Markdown，可直接贴）**：

```markdown
---

上面五条报错都是真的，也都是我自己踩过的。但真实工作中你遇到的报错不会是这五条 ——
总会有些没见过的。

我在做的一件事是：把报错**直接贴进一个页面**，它去提取里面的 API 名和类型名，
定位到相关的中文文档小节，并给出**可以点回原文的引用**（引用不只是一句"参考文档"，
是能点开、能看到原文片段、能看到这段译文对着哪次上游提交译的）。

地址：https://effect-ts.cn/debug/

**它的边界我也说清楚**，免得你贴进去失望：

- 报错里出现**具体 API**（`Effect.runPromise`、`Layer.succeed` 这种）时，定位比较准；
- 报错里**只有类型名、没有任何 API 调用**时，目前定位还不理想 ——
  这种情况用上面那套"读三个位置"的方法更管用。

换句话说：它能帮你的，是那些"报错里提到了某个我没见过的 API"的场景。
真正只有类型名在打架的时候，还是得靠你自己读。

（对了，它对你贴进去的报错不做别的用途，也不要求登录。）
```

## 插入段 B —— 给第二篇《TypeScript 后端那些你自己手写的样板》

**放哪里**：放在「怎么开始」一节的末尾，紧跟那段"先让一个函数跑通"之后。
理由：这一节的读者正处于"我要不要动手"的犹豫期，这时候给他一个**低成本的求助出口**最有用。

**插入内容（Markdown，可直接贴）**：

```markdown
---

开始写之后你一定会碰到"这个词到底什么意思"的时刻 —— `Layer`、`Scope`、`Fiber`、`Schedule`。

站上有一个可以问的入口：**https://effect-ts.cn/ask/**

它只从官方文档的中文译文里找答案，每条回答都带**可以点回原文的引用**。
**找不到依据时它会直接说"文档里没有讲"**，不会编一个看起来对的答案给你 ——
这一点我特意让它这样：学一个新东西的时候，一个编出来的解释比一句"不知道"危险得多。

所以它的用法是"帮我快速定位到官方怎么说"，而不是"替官方解释"。
```
