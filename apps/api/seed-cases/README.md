# seed-cases —— 报错百科的播种用例库

这里的每个 `.ts` 文件都是**真的会失败**的代码。`scripts/seed-errors.mjs` 跑一遍它们、
取**真实报错**喂给 `/debug`，让报错百科的条目一次性成型，而不是等用户一条条问出来。

## 为什么放在 `apps/api/` 下

因为要能解析 `effect` 包。`apps/api/tsconfig.json` 的 `include` 只有 `["src", "test"]`，
所以这个目录**不会被 `pnpm typecheck` 扫到** —— 这是必须的，因为里面的代码是故意写坏的。

## 一条规则，不需要元数据

跑批的判据只有一条：**先 `tsc`；编译器不报错，就实际运行它。**

于是"编译期类型报错"与"运行期报错"用同一套流程处理，用例文件上不需要标任何东西。

## 加一个用例

1. 建文件，命名 `NN-短描述.ts`（数字只用于排序）。
2. **编译期用例**：写一段会编译失败的 Effect 代码即可。
3. **运行期用例**：写一段**能编译、但运行时会崩**的代码，并用应用级错误处理器打印：
   ```ts
   Effect.runPromise(program).catch((e) => { console.error(String(e)); process.exit(1) })
   ```
   这么写是为了产出**用户真正会复制的形态** —— `(FiberFailure) Error: ...`。
   顶层 `await` 也能崩，但 Node 打印的是 `Error: ...`（没有 `(FiberFailure)` 前缀），
   而那正是 `fiber-failure` 模式赖以识别的特征串。
4. 跑 `node scripts/seed-errors.mjs --dry --only <你的文件名片段>` 看它产出什么报错。

## 写作纪律

- **不要手写报错文本。** 报错必须由 `tsc` 或 `tsx` 实际产生 —— 每条都能被独立复现，
  百科里的条目才站得住。
- **运行期用例要忠实。** `Service not found` 在真实世界里的来源是"类型在某个边界上被擦掉了"
  （库的入口函数内部 `as` 掉了 R，或使用方自己 `as any`）。
  所以用例里也要有这个擦除动作 —— 直接写 `runPromise(需要依赖的effect)` 是**编译不过**的，
  那测的就不是运行期路径了。

## 现状（2026-09）

| 类别 | 能产出实质答案 |
| --- | --- |
| **运行期报错**（间接撞上 Effect 的人看到的） | **7 / 7** |
| 编译期类型报错（Effect 使用者写错的） | 1 / 7 |

运行期这一类靠 `packages/knowledge/src/error-patterns.ts` 的**确定性模式表**接住。

**编译期这一类目前是短板**：纯类型报错的信号在类型名上，而检索的标题兜底会落到
《为什么选择 Effect？》《Effect Schema 简介》这类引言页，答案于是变成"根据现有文档无法确定"。
要真正解决得做一个**面向类型报错的检索模式**（按类型表达式匹配小节标题），那是独立的一件事。

跑批脚本会把这些列出来，**不达标的条目不会自动删除**（删除不可恢复），
请人工看 `scripts/.seed-report.json` 里的明细再决定。
